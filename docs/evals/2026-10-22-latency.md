# Eval: slow answers and visible progress (2026-10-22)

**The report.** Some answers took a long time, and the reader saw nothing happen. The goal: every answer shows live progress, and the slow ones get faster.

## What was measured

`scripts/eval_ai_quality.py latency` asks 12 questions (11 English, 1 Hebrew; short, medium and one request for a detailed answer) through the same steps `/ask` runs, one at a time, on the real models. It records the time to the first progress event, the time to collect sources, the time in the model call, the total, which model answered and which progress steps were reported. The harness turns off Supabase, Sentry and the shared Redis. Gemini and Claude are run separately (`--provider claude` turns Gemini off).

Answers are not streamed token by token (the model returns one JSON object), so there is no "first token" to time. The reader waits for the whole answer and watches the progress line meanwhile.

## What was slow

| Cause | Evidence | Fix |
|---|---|---|
| Claude spent most of its time thinking. Haiku 5.5 thinks by default and a short answer is a JSON object built from sources already in the prompt | Claude median 6.6 s, up to 9 s for a one-line answer | `thinking: {"type": "disabled"}` on every Claude answer below the long-answer ceiling. A long or detailed answer keeps thinking (see below) |
| Gemini fails now and then (429, 503, 504) and the answer falls to Claude | One Gemini row was 16.3 s before and one 20.9 s in the second run: a failed first call, then Claude | Not removed: the fallback is the point. It is now shown to the reader (below) |
| Nothing told the reader why a step took long | The progress line named only five stages | Four new named steps |

## Visible progress

The client shows "Getting started" the moment the question is sent. The stream then names five stages (sources, commentary, customs, times, thinking) and, inside a stage, a `detail` that says what it is doing. This change adds the `step` detail kind, set while the answer is being written, with four values:

| Step | When | English | Hebrew |
|---|---|---|---|
| `long` | the reader asked for a long answer | Writing a long, detailed answer | כותבים תשובה ארוכה ומפורטת |
| `retry` | Gemini answered 429, 503 or 504 and is being asked again | The first model is busy, trying again | המודל הראשון עמוס, מנסים שוב |
| `second_model` | Gemini failed and Claude takes over | Asking a second model | פונים למודל נוסף |
| `second_look` | the model flagged the question out of scope and is asked once more | Taking a second look | בודקים שוב |

The web lookup line now reads "Searching trusted sites" / "מחפשים באתרים מהימנים". The wording lives in `static/js/ask-progress.js` (the server sends data, not prose). It covers the search-bar answer, the follow-up in a conversation and the mini widget, since all three read the same stream. A step the client has no words for is ignored.

`first_progress_seconds` was 0.0 in every row of both final runs: the first stage begins before any I/O. In a real request the conversation route first validates the question, checks the owner and the cost gate and saves the reader's message, then starts the stream; the client's own "Getting started" covers that gap.

Claude's typical answer is now about three times faster. Gemini's median did not change (it was already fast); its slowest row went from 16.3 s to 4.2 s, but that is the absence of a Gemini failure in the run, not a fix: an earlier "after" run had a 20.9 s row from a failed first call. "Claude before" is the same code path with thinking on that `4972344` and the commits up to `f75bcd0` use, run on the same 12 questions.

## The thinking trade-off

Turning thinking off for every Claude answer was faster still (median 3.0 s, 12 rows) but shortened the long answers: median 297 words against about 546 with thinking on, for the same ten long-answer prompts. Long answers matter more than a second saved, so thinking stays on from the long-answer ceiling up (`LONG_ANSWER_MAX_TOKENS`, 4,096) and the study ceiling, and is off below it. Rerun of the ten long prompts on the final code: median 492 words on Claude (17 s median) and 478 on Gemini (5 s). The detailed Hebrew question above (284 words, 20.8 s) is the cost: it is inside the 45-second budget.

## Tests

`tests/test_model_progress.py` (5): an ordinary answer reports no step; a long request reports `long`; a failed first model reports `second_model`; a flagged question reports `second_look`; a Gemini retry reports `retry`. `tests/test_ask_progress.py` (a model step is a detail and an unknown one is dropped), `tests_js/ask_progress.test.js` (both languages for each step and the web line), `tests/test_answer_pipeline_upgrade.py` and `tests/test_anthropic_model_pin.py` (thinking off for a short answer, on with headroom for a long one, the agentic turn unchanged).

## Known limits

- One run per provider, 12 questions, on live models whose speed changes with load. The direction (Claude about 3x faster) held on three runs; the single numbers are not a guarantee.
- A request for a long answer on Claude is still 12 to 21 s. The only way to make it faster is a shorter or thinner answer.
- The `primary` source-collection step can still take up to its 15-second ceiling when Sefaria is slow. Not changed here.
- A real iPhone's network was not part of this measurement; everything above is from this computer.
- The "hack into a neighbour's wifi" off-topic case in the refusal eval is answered with a short halachic "forbidden" (no instructions) when Claude does not think (13 of 14 correct refusals on Claude, 14 of 14 on Gemini). I accepted that: the answer refuses and teaches nothing harmful.
